The Lotus extension recognizes `.lt` files. It provides syntax and semantic highlighting, snippets, field and method completion, hover information, go to definition and an outline for the current document.

## Install from source

The extension lives in the `tools/lotus-extension` submodule, maintained in [lotus-extension](https://github.com/LINQeee/lotus-extension).

```sh
git submodule update --init --recursive
cd tools/lotus-extension
npm ci
npm test
npm run package
code --install-extension dist/lotus-extension-0.1.3.vsix
```

Alternatively, use **Extensions: Install from VSIX** in VS Code. The extension requires VS Code 1.85 or newer. Packaging uses a current Node.js release compatible with the dependencies.

## Configure the compiler

Install or build [Lotus](/quickstart), then open VS Code settings and search for **Lotus**.

| Setting | Default | Purpose |
| --- | --- | --- |
| `lotus.compilerPath` | `lotus` | Executable in PATH, an absolute path or a workspace-relative path |
| `lotus.librariesPath` | Empty | Optional runtime directory passed as `--libs` |
| `lotus.diagnostics.enabled` | `true` | Check files on open, save and while typing |
| `lotus.diagnostics.delay` | `300` | Delay after typing before checking, in milliseconds |
| `lotus.diagnostics.timeout` | `10000` | Check timeout in milliseconds |

For a compiler checkout, workspace settings can contain:

```json
{
    "lotus.compilerPath": "./cmake-build-debug/lotus",
    "lotus.librariesPath": "./libs"
}
```

On Windows, include `.exe` in the compiler filename. Paths are passed as process arguments, so paths with spaces do not require extra shell quotes. In a multi-root workspace, relative paths resolve against the folder containing the document.

## Commands and errors

Use the command palette:

- **Lotus: Check Current File** checks the current editor text without saving.
- **Lotus: Run Current File** saves and runs it in a VS Code task.
- **Lotus: Build Current File** saves and builds an executable in a VS Code task.
- **Lotus: Show Compiler Output** opens the check log with the compiler command and working directory.

Compiler execution requires a trusted workspace. Syntax and navigation remain available without trust. The extension does not download or install a compiler.

Automatic checks run on open, save and after a short pause while typing. They use temporary snapshots of the editor text, including unsaved changes; the original file is not overwritten. New unsaved editors work when their language mode is Lotus. Each edit cancels the previous check and clears outdated diagnostics. Temporary snapshots are removed after checking.

Compiler errors with source positions appear in Problems and as underlines. Errors without coordinates, missing executables and timeouts appear in the Lotus language status and **Lotus** output channel. They do not underline the first line of the file.

If `lotus` reports `Unknown symbol: .`, check whether `lotus.compilerPath` points to an older installation in PATH. Build the current compiler and set the path explicitly, for example `./cmake-build-debug/lotus` in a compiler checkout. The current class declaration keyword is `class`, not `type`.

The compiler currently stops at its first error. The extension therefore reports one compiler error per check, not a full list of independent errors.

## Highlighting

Class names are highlighted in declarations, variable types, parameter and return annotations, and object constructors. Fields, parameters, variables and function calls have separate token categories. Semantic highlighting also distinguishes references to declared classes and parameters in the current document. Colors come from the active VS Code theme.

## Completion and navigation

Completion uses declarations in the current document. It supports typed variables, parameters, class fields and methods, `this`, nested named receivers and array `.length`. Built-in functions and language keywords are also suggested. Snippets provide templates for classes, functions, conditions and loops.

This is a lightweight declaration analyzer, not a full language server. It does not infer receivers from arbitrary expressions or method return chains, provide cross-file symbols, rename symbols or format programs. Incomplete code may yield incomplete suggestions.

The extension supplies a default `.lt` file icon. Its visibility depends on the active file icon theme; themes with their own Lotus association can override it.

## Develop the extension

Open `tools/lotus-extension` itself in VS Code and run **Run Lotus Extension** with F5. A separate Extension Development Host opens with the extension loaded. Open a Lotus project there and configure the compiler path.

Run `npm test` for declaration analysis, semantic tokens, diagnostic positions and TextMate grammar checks. `test/host.js` also exercises these features in an Extension Host, including diagnostics without saving; run it only with a disposable workspace and test profile. Keep language examples and user documentation in this compiler repository.


## Local development without VSIX installation

From `tools/lotus-extension`, run `npm run dev`, then open your Lotus project in the new Extension Development Host window. It loads the local source directly. Use **Developer: Reload Window** after changing extension code or configuration. This does not update the extension installed in your regular VS Code windows.

## Builds and releases

Node.js 22 or newer is required for packaging and publishing.

| Directory | Purpose | Stored in Git |
| --- | --- | --- |
| `dist/` | Local packages and CI build output | No |
| `releases/` | Versioned VSIX packages approved for publication | Yes |

`npm run package` builds into `dist/`. CI checks every push and pull request and attaches the package as a workflow artifact.

To release a new version from the extension repository:

```sh
npm version patch --no-git-tag-version
npm run release:prepare
git add package.json package-lock.json releases/
git commit
git push origin main
```

Commit the implementation changes with the package too. `release:prepare` runs tests, builds a VSIX and copies it to `releases/`. It refuses to overwrite an existing release file: published versions are immutable. Keep earlier release packages in that directory.

A push changing `releases/*.vsix` on `main` runs `.github/workflows/release.yml`. It verifies that the package identity, version and implementation match the checked-out source, creates a `vX.Y.Z` GitHub Release and attaches the committed VSIX. The Marketplace job publishes the same file. A manual workflow run can retry publication; an existing GitHub asset must match byte-for-byte, and an already published Marketplace version is skipped.

### One-time Marketplace setup

GitHub Releases work immediately with the workflow's built-in GitHub token. Marketplace publication remains disabled until the publisher is configured:

1. Sign in to [Marketplace publisher management](https://marketplace.visualstudio.com/manage) and create publisher ID `LINQe`. If that ID is unavailable, update `publisher` in `package.json` and rebuild before publishing.
2. In the publisher's **Trusted Publishing** settings, create a policy for owner `LINQeee`, repository `lotus-extension`, workflow `release.yml`. Leave Environment empty.
3. In the GitHub repository's **Settings → Secrets and variables → Actions → Variables**, add `MARKETPLACE_ENABLED` with value `true`.
4. Run **Release VSIX** from the Actions tab to publish the current release.

The workflow uses `vsce --oidc` and `id-token: write`; no PAT secret is required. See [VS Code's Trusted Publishing instructions](https://code.visualstudio.com/api/working-with-extensions/publishing-extension#publish-with-github-actions-and-trusted-publishing).
