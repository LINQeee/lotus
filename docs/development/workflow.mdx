Start with [Quickstart](/quickstart), then read `AGENTS.md` for the project's C, JavaScript and documentation style.

## Prepare the checkout

```sh
git submodule update --init --recursive
npm ci --prefix tools/lotus-test
./scripts/install-iwyu.sh
./scripts/install-hooks.sh
```

Contributor tools: Node.js 20+, Python 3, clang-format 22 and IWYU 0.26, in addition to the build toolchain. The IWYU installer builds into `.tools/`; Python is used by include analysis, not the test runner.

Shell scripts read `lotus-scripts-config.json`; the runner reads `lotus-test-config.json`. Set each `cmake` field to your CMake command or path. `CMAKE` in the environment overrides both. IDE hooks inherit the IDE's environment.

## Verify a change

```sh
./scripts/style.sh --write
node tools/lotus-test/bin/lotus-test.mjs
node --test scripts/test-cli.mjs
./scripts/style.sh --check
```

The runner builds the compiler and runtime. While iterating, select a feature such as `loops/for`; see [testing](/development/tests).

| Command | Scope |
| --- | --- |
| `style.sh --write` / `--check` | Include cleanup and C formatting |
| `format.sh --write` / `--check` | C formatting only |
| `includes.sh --write` / `--check` | Includes only |

Register new C files in the relevant CMake target. Formatting does not cover `.lt` files. For CLion, select the pinned clang-format executable as the formatter; use the repository's `.clang-format`.

<Accordion title="Tool overrides">
`CLANG_FORMAT`, `IWYU_BINARY`, `LLVM_CONFIG` and `CMAKE` select tool locations. A custom IWYU installation needs matching `iwyu_tool.py` and `fix_includes.py` beside its binary. Script config paths are relative to the project root.
</Accordion>

## Commit and push

Hooks check formatting/includes in the staged snapshot before commit and outgoing commits before push. Both then run language and CLI tests from the **working tree**. Any failure blocks the operation; hooks do not rewrite or stage files.

Local hooks can be bypassed. Shared enforcement requires CI; the local test run is not a test of an isolated staged snapshot.

## Repositories

| Checkout | Repository |
| --- | --- |
| Compiler and docs | [lotus](https://github.com/LINQeee/lotus) |
| `lotus-core/` | [lotus-core](https://github.com/LINQeee/lotus-core) |
| `tools/lotus-test/` | [lotus-test](https://github.com/LINQeee/lotus-test) |

Commit and push submodule changes in their repositories first, then commit updated pointers in Lotus. After pulling, run `git submodule update --init --recursive`; reinstall runner dependencies when its lockfile changes.
